## Apply order

The two files are independent at apply time but **not** at runtime — `ocr.py`'s
new branch calls into `ocr_trocr.py`. Apply `ocr_trocr.py` first so the
dependency exists before anything can reach it.

1. **`app/inference/ocr_trocr.py`** — lazy checkpoint resolution, fail-fast
   guard, explicit mode log, inference lock.
2. **`app/inference/ocr.py`** — `OCR_RECOGNIZER` selector, TrOCR dispatch in
   `run_ocr_on_crop`, docpp-off retry skip.
3. **Clear the `.pyc` cache** — `rm -rf app/inference/__pycache__/`. A stale
   `ocr.cpython-310.pyc` newer than the source has already caused one benchmark
   in this project to silently execute pre-edit code.
4. **Verify the no-op path first.** With `OCR_RECOGNIZER` unset, re-run the
   PaddleOCR cascade on the quick sample and diff against the pre-patch result
   CSV. It must be byte-identical. Do this before touching TrOCR at all — it
   isolates "did the patch change Paddle behaviour" from "does TrOCR work."
5. **Then** set `OCR_RECOGNIZER=trocr` and `FINETUNED_TROCR_MODEL_DIR=<dir>`.

## The one change that needs empirical sign-off

**Spec item 3 — skipping the docpp-off retry (`ocr.py`, `_try_extract_best_valid`).**

Output-neutrality is **asserted from code reading only**. The reasoning: the
TrOCR branch ignores `docpp_off`, so the retry re-runs generation on identical
pixels and reproduces pass 1. The supporting evidence — `docpp-off-retry` never
appears in any TrOCR run's tier counts — is consistent but weaker than it looks,
because that counter only tallies *valid* results. Absence of a successful retry
is not absence of a differing retry.

**Required before trusting it:** run the full cascade benchmark twice on the same
checkpoint, once with the guard active and once without, and diff the result
CSVs. They must match apart from runtime. Until that diff exists this is an
optimisation on probation, and its failure mode is silent — it would drop a retry
that would have validated.

If you want the parity result sooner, apply items 1, 2, 4, 5, 6 and leave item 3
out; the rest of the patch does not depend on it.

## Amendments incorporated

- **Spec item 5** now also emits a startup line naming the resolved weights
  source and stating outright whether the model is fine-tuned or the hub base.
  The base-model case logs at **WARNING**, not INFO — the whole point is that
  this failure is invisible in output, so it must not sit at the same level as
  routine chatter.
- **New item:** `_trocr_lock` extended to cover `model.generate()`, not just
  init. Note the hazard called out in the patch comments: `threading.Lock` is not
  reentrant, so `run_trocr_on_crop` calls `get_trocr()` *before* acquiring it.
  Nesting them self-deadlocks on first use. If they ever need nesting, switch to
  `threading.RLock()` in the same commit.

**Unverified premise, flagged:** the `--threads 4` gunicorn setting is taken from
your description of the deployment. `gunicorn==26.0.0` is in `requirements.txt`
but I found no gunicorn config, systemd unit, or launch script in the repo that
sets thread count — so I could not confirm it from the code. The serialisation
decision holds regardless (one generate saturates the CPU at any thread count
above 1), but the specific number is your input, not a repo fact.

## Known limitation (found 28-07-2026, applying the Tier 3 TrOCR gate)

`_best_portrait_rotation`'s tie-break (`conf_90 >= conf_m90`) is meaningless
under TrOCR, since TrOCR's confidence is a hardcoded 1.0 placeholder for both
rotations. This only activates when BOTH rotations already fail to validate
(`is_valid` is unaffected either way) — it only decides which garbage OCR
text is shown as a hint for manual correction on rows already flagged
invalid. Biased toward +90 unconditionally. Not fixed due to remaining
timeline; a real fix would need a TrOCR-appropriate tie-break signal since
confidence isn't meaningful here.
